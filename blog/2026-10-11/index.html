Capillaries: scalability updates

What has changed

Basic test settings remain the same:

  • number_of_daemons = number_of_cassandra_nodes
  • Cassandra nodes are x4 more powerful than Capillaries instances
  • daemon's GOMEMLIMIT is still at 75%

There were a few changes since the last scalability update in May 2026.

Lookups with async SELECTs

When handling lookups, Capillaries used "IN" condition in SELECT statements, which is widely considered an anti-pattern. Since version 1.2.2, Capillaries runs multiple async SELECT commands to retrieve index records by key and data records by rowid. As a result, we get a much better use of resources - Cassandra does not have to perform internal read requests and achieve a quorum consensus. The CPU use chart for the lookup nodes handling in the portfolio test looks much better:

Test deployment changes

For daemons, GOGC=100 setting was replaced with GOGC=25, which gives us a bit more organized picture for the go_memstats_heap_inuse_bytes{job="go_exporter"} Prometheus metric - memory consumption does not jump back and forth as it used to (32 daemons and 32 Cassandra nodes runs, before and after):

More important: daemon_thread_pool_factor setting was switched from 3 to 2. 2 worker threads per daemon instance CPU instead of 3. 3 threads turned out to be too aggressive: during py_calc node handling, each thread has to spawn its own copy of Python, and too many python tend to cause OOM errors (especially starting Python 3.13 with its JIT compiler and no-GIL mode). To compensate, the number of Cassandra writers were slightly increased (see daemon_writer_workers variable).

As before, portfolio test (996 ARK-inspired stock portfolios with 14,683,696 transactions and 713,800 end-of-month holding records) is used for performance benchmarking. The updated results are presented below.
